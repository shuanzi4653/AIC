## 1. P1 · 现场会看见或会被追问的

### P1-1 并发 6 即明显退化（性能）

**证据**

| 场景 | 结果 |
|---|---|
| 单请求 `nation?level=nation&minute=60` | 1.12 s / 592 856 B |
| 单请求 `minute=0`（冷） | 3.32 s / 619 263 B |
| 并发 6 × 3 轮（不同 minute） | 18/18 成功，**中位 5.21 s，峰值 23.19 s**（⚠ 见下方更正） |
| 一致性（同 minute 连打两次） | traffic 完全一致，字节数相同（605 464 = 605 464） |

**根因（2026-11-24 18:15 更正，必读）**：

上面的 5.21 s **主要是测量方法造成的**，不是服务器并发能力。压测脚本没发 `Accept-Encoding`，
每次拉的是 617 KB 未压缩体；补测后：

| 场景 | 耗时 | 传输量 |
|---|---|---|
| 服务器内部（绕过公网）单请求 | **0.035–0.062 s** | — |
| 服务器内部 同帧 6 并发 | **0.16–0.21 s** | — |
| 服务器内部 不同帧 6 并发 | **0.13–0.26 s** | — |
| 公网 + gzip（浏览器真实情况） | **0.45 s** | 112.9 KB |
| 公网 未压缩（脚本当时的情况） | 0.86 s | 617.8 KB |

真正的成本在"整包重传"，不在锁：`_NATION_LOCK` 仍让不同帧串行，但单帧构建只要几十毫秒
（Python 内部命中缓存 0.044 s），2 核完全撑得住。所以本条的正确表述是
**"弱网下每帧 600 KB 的重复传输"**，修法也应当是 ETag/304 + 薄载荷，而不是重写并发模型。

V1.1.5 已做：载荷缓存 + single-flight（同帧并发 6 → 0.18 s）、ETag/304（重复帧 0 字节）、
Java 字节透传（去掉 600 KB 的 readValue→再序列化）。

**影响**：总决赛现场若有 2–3 位评委同时打开或刷新，第三人开始明显等待；前端每拖一格时间轴都是一次全量请求，叠加后更糟。

**修法（二选一）**
- A（小改）：锁内只做"查缓存 + 取快照"，把重算挪到锁外，用 single-flight（同一 key 只允许一个线程算，其余等结果）
- B（中改）：按 `(level, id, minute, virtual)` 做载荷快照缓存（TTL 15–30 s），锁只保护缓存写入

**验收判据（更正后）**：服务器内部 6 并发中位 ≤ 0.5 s；公网重复请求命中 304（传输 0 字节）；
同 minute 两次结果完全一致。

### P1-2 城市层"在飞"只算始发，与"航线数"口径不一致

**证据（实测 minute=60，辽宁省）**

| 城市 | 航线 | 在飞 |
|---|---|---|
| 锦州市 | 4 | 1 |
| 葫芦岛市 | 2 | 1 |
| **沈阳市** | **12** | **0** |
| 大连市 | 4 | 0 |
| 营口市 | 3 | 0 |

13 个市里 **11 个"航线 > 0、在飞 = 0"**，而全省在飞 2 架。

**根因**：`nation.py:1427` `origin = [f for f in flights if f.get('fromName') == city.get('name')]` —— 在飞/停飞只数**始发**；而 `_slice_corridors(city=...)`（`nation.py:904`）把**以本市为终点**的航线也算进来。于是同一行里"12 条航线"含进出港，"0 架在飞"只含始发。

**影响**：评委逐级下钻"全国 → 大区 → 省 → 市"，最后一级看到的是一座有 12 条航线却没有一架飞机的城市。

**修法**：`_city_totals` 的 `airborne / hold / delayed` 改为"起或降在本市"（`fromName == city or toName == city`），并在界面标签注明"含飞入"；若坚持始发口径，则航线数也改成只算始发（两者必须同口径）。

**验收判据**：任选一省，各市 `airborne` 之和 ≥ 省 `airborne`（含重复计数时要写明），且不存在"航线 > 0 而在飞 = 0"的市（除非该市确实无班次）。

### P1-3 雷达中继降级路径必然失败（且刷控制台红字）

**证据**（无头 Edge 打开线上首页，控制台抓取）

```
Access to fetch at 'https://image.data.cma.cn/tiles/China/RADAR_L3_MST_CREF_GISJPG_Tiles_CR/20261124/17/42/3/2/5.bin'
from origin 'https://tianchuang.shuanzi.site' has been blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present on the requested resource.
```

一次加载出现 **8 条**同类报错。

**根因**：`frontend/src/traffic/radarRelay.js:38` 用浏览器 `fetch(tileBase + …)`，`{ mode: 'cors' }` 直连 `image.data.cma.cn`。该源不返回 CORS 头，浏览器侧**不可能成功**；后端 `POST /traffic/radar/tiles`（`main.py:1150`）因此永远收不到中继数据。触发条件是后端把 `relay.needed` 置为 `true`（即主路径缺瓦片）。

**影响**：主路径正常时无害；一旦缺瓦片（今天 17:42 这帧就发生了），降级救不回来，还会在录屏里留下红字。

**修法（二选一）**
- A：改成同源代理 —— 后端新增 `GET /api/traffic/radar/tile?slot=&z=&x=&y=`（服务端去取，无 CORS 限制），前端只请求自家域名
- B：彻底关掉中继，缺片时在雷达行明写"本帧缺 N 片（源站未发布）"，并删掉 `/traffic/radar/tiles` 路由

**验收判据**：首页控制台 CORS 报错 0 条；人为构造缺片时界面有明确提示。

### P1-4 时间轴首尾不是同一帧（minute 0 ≠ 1440）

**证据**

| minute | 在飞 | 停飞 |
|---|---|---|
| 0 | 124 | 15 |
| 1440 | 102 | 12 |

两者按"一天"的语义应是同一时刻。

**根因**：`elapsed = (minute - phase) % headway`，1440 不是各走廊 `headway`（150–270 分钟）的整数倍，所以 `(1440 - phase) % headway ≠ (0 - phase) % headway`。

**影响**：时间轴拖到最右与拖回最左，数字不一致；讲解"全国一天运力"时会自相矛盾。

**修法**：入口处 `minute = int(minute) % 1440`（1440 归一为 0），或时间轴上限收到 1439 并在界面标注。

**验收判据**：`minute=0` 与 `minute=1440` 的 `traffic` 完全一致。

### P2-2 `/api/traffic/v2/modelcard` 与全国判据不是同一个模型

**证据**

| 来源 | 模型 | 维度 | 训练数据 |
|---|---|---|---|

- A：下线该路由（连 Java 白名单一起删），模型信息统一由 `/modelcard` 之外的新入口给 v3
- B：修好字段并改指 v3，返回 `features` 28 项、`trainedAt`、`auc/brier/ts`

**验收判据**：接口返回的 `modelVersion` 与 `models/ml-v3-national-vis.json` 一致；`tasks[].modelVersion` 无 null。

### P2-3 大载荷无缓存协商

**证据**：`nation` 单次 592–619 KB（gzip 已开，`Content-Encoding: gzip`），响应头**无 `Cache-Control`、无 `ETag`、无 `Last-Modified`**。

**影响**：时间轴每拖一格就全量重传一次；弱网下就是"拖一下卡两秒"。

**修法**：加 `ETag`（由 `(level, id, minute, radar_ts)` 派生）+ `Cache-Control: private, max-age=30`；或按 minute 出增量（只回 `flights` 与变化字段）。

---

### P2-4 非法 `policy` 静默回退

**证据**：`GET /api/traffic/v2/nation/zones?policy=WHATEVER` → 200，返回 `policy: "APPROVAL_REQUIRED"`。

**影响**：写错参数的人以为生效了。净空是"一律禁止 / 可申请"两档的演示开关，回退错档会讲错话。

**修法**：非法值返回 400 并列出允许值（`PROHIBITED|APPROVAL_REQUIRED`），前端仍传合法值不受影响。

## 5. 三个视角的小结

**用户视角**
- 下钻到市会看到"有航线、没飞机"（P1-2），这是最容易被当场指出来的一条
- 时间轴拖到两端数字对不上（P1-4）
- 弱网拖时间轴卡顿（P1-1 + P2-3）

**企业视角**
- 并发能力只有"2–3 人同时看"的水平（P1-1）
- 仓库有两套后端源码，交付物看起来不专业（P2-1）
- 缺 CSP，安全头不完整（P3-2）
- 备案、证书、HSTS、X-Frame-Options 均合规

**研究院视角**
- 模型卡接口给的是 3 站 v2，正文讲的是 319 城 v3（P2-2），这是"同一份材料里两个模型"的隐患
- 载荷无 ETag，无法证明"同一 minute 两次结果一致"之外的缓存语义（一致性本身已实测通过）
- 阈值单点下发已核实一致：rules 0.35/0.75、model 0.35/0.60、VIS 1500/3000/5000 → 0.72/0.45/0.22、cost 1.0/0.6/0.02
