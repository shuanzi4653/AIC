# 运维：预热、资源配额与定时任务（V1.1.5）

> 适用环境：`tianchuang.shuanzi.site`（2 核 3.7 G 共享机，同机还有 zhuheng / wisdiet / ice-travel 等站点）
> 一句话：**任何人打开页面前，系统已经是热的；预热再重，也不许把 CPU 吃满**。

---

## 1. 三层预热

| 层 | 位置 | 频率 | 作用 | 代价 |
|---|---|---|---|---|
| 启动预热 | `backend-python/main.py` `_startup_warm()` | 每次服务启动 | 全国层 t+3 s；旧轨建场 t+90 s / t+150 s | 首屏只等第一层 |
| 常驻保活 | 同文件 `_keep_warm()` | 每 15 秒 | 把默认帧（minute=60）重算一次，缓存永远新 | 40 ms / 15 s ≈ 0.3% 一核 |
| 定时预热 | `aic-warm.timer` → `bin/warm-now.sh` | 每天 08:05 / 12:05 | 打 7 个关键端点并打印耗时，作为"系统还活着"的定期证据 | 约 2 秒 |

### 为什么顺序是"3 / 90 / 150"

旧顺序在 t+5 s 就同时起两个通道的 `traffic_service.session()`（各几十秒 CPU），t+11 s 再算全国载荷。
实测部署后 **1–3 分钟 CPU 一直是 100%**，这段时间任何人打开页面都在排队——而"刚发完版看一眼"正好撞上。
新顺序把首屏真正需要的全国层提到最前，旧轨建场往后推，中间留 90 秒给访客。

### 为什么 keep-warm 比定时预热重要

national 载荷的缓存 TTL 是 20 秒。四小时前预热出来的结果早就过期了。
`keep-warm` 每 15 秒续一次，效果是"任意时刻的首次访问都命中缓存"（实测 40 ms 出 600 KB）。
定时器解决的是另一件事：定期确认端点可达，并留下带时间戳的耗时表，出事时能定位是哪一段慢。

## 2. 手动预热

```bash
# 服务器上（只读，不重启任何服务）
sudo systemctl start aic-warm.service
sudo journalctl -u aic-warm.service -n 12 --no-pager

# 直接跑脚本（等价）
/opt/apps/AIC-tianchuang/bin/warm-now.sh
```

输出长这样（每一项都带耗时）：

```
[2026-11-24 18:37:56] warm start
health                     200    0.00s
nation(minute=60)          200    0.08s
flights(minute=60)         200    0.02s
constants                  200    0.00s
overview                   200    1.82s
modelcard                  200    0.00s
zones                      200    0.06s
[2026-11-24 18:37:58] warm done fail=0
```

任一端点非 200 → 脚本退出码非 0（`systemctl status` 里能看到 failed），但**不会**去重启服务。

本地演示前也可以跑仓库自带的 `tools/probes/_warmup_demo.py`（打公网域名，含城市层下钻）。

## 3. 资源配额

| 单元 | 配额 | 文件 |
|---|---|---|
| `AIC-tianchuang.service`（Java） | `CPUQuota=130%`、`MemoryMax=1024M` | `/etc/systemd/system/AIC-tianchuang.service.d/cpu.conf` |
| `AIC-tianchuang-python.service` | `CPUQuota=110%`、`MemoryMax=1024M` | `/etc/systemd/system/AIC-tianchuang-python.service.d/cpu.conf` |
| `aic-warm.service` | `Nice=10`、`TimeoutStartSec=600` | `/etc/systemd/system/aic-warm.service` |

核对：

```bash
systemctl show AIC-tianchuang -p CPUQuotaPerSecUSec   # 期望 1.300000s
systemctl show AIC-tianchuang-python -p CPUQuotaPerSecUSec  # 期望 1.100000s
```

2 核 = 200%。两个单元合计 240%，允许策略性超配（不会同时满载），同时给 nginx 与同机站点留出余量。
配额的代价是"预热更慢"（旧轨建场从 ~60 s 拉到 90 s 量级），换来的是"访客不被挤"。

## 4. 定时任务

```bash
systemctl list-timers aic-warm.timer     # 看下次触发
sudo systemctl disable --now aic-warm.timer   # 关掉
```

`*.timer` 里 `Persistent=true`：机器重启错过时间点，开机后补跑一次。

---

## 5. 已知边界

- **配额不等于隔离**：CPUQuota 只限本单元总量，同机其他站点仍会争抢物理核。2 核机器上"多人同时拖时间轴"仍旧会变慢，这是硬件上限。
- **keep-warm 与请求共用一把锁**：`keep-warm` 拿的是 nation 模块的串行锁，抢到锁的那 40 ms 里访客请求要等。频率 15 秒、单次 40 ms，概率可忽略，但如果把间隔压到 1 秒就会明显了。
- **定时预热不刷新旧轨计划**：`warm-now.sh` 只打 HTTP 端点，不触发 `traffic_service.session()` 重建。反事实页首次访问仍可能 40–90 秒（那是重算整份计划，不是预热能解决的）。
- **改 unit 后必须 `systemctl daemon-reload`**，否则新配额不生效。
