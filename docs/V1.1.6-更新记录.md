## 一、改了什么

### 1. 预热从"人跑脚本"变成"页面自己跑"

| 项 | V1.1.5 | V1.1.6 |
|---|---|---|
| 触发方式 | 人工执行 `python tools/probes/_warmup_demo.py` | 页面 `load` 后 4 秒自动，一个标签页一次 |
| 覆盖范围 | health / nation / flights / evidence / constants / city | 常量 → 总览 → 班次列表 → 某个在飞班次的取证链 |
| 失败行为 | 脚本退出码 1，提示"红了别上台" | 全部静默：预热没热成不等于功能坏了，不弹错、不进 console |

实现：`frontend/src/traffic/prefetch.js`（新），在 `TrafficWorkbench.vue` 的 `onMounted` 里调用 `runPrefetch()`。
顺序与 `_warmup_demo.py` 同一套（轻的先来），但**延迟 4 秒启动**、**串行**，不与首屏地图抢连接。

### 2. 反事实预建（解决 40–90 秒首次等待）

| 项 | 内容 |
|---|---|
| 端点 | `POST /api/traffic/v2/counterfactual/prewarm?seed=42&scenario=live` |
| 行为 | 先查 `traffic_service.session()`：已 READY 直接返回 `READY`；否则起**后台线程**跑一次 `counterfactual`（内部完成建场 + 对照计算），请求立刻返回 `PREWARMING` |
| 节流 | 同一 `(seed, scenario)` **60 秒内**只触发一次，重复请求返回 `THROTTLED`（带 `ageSeconds`） |
| 为什么不做定时预建 | 计划 key 绑当前雷达帧与天气快照（`service.identity(...)` 含 `snapshot_id` 与 `radar_id`），帧一变就要重算；2 核机器上定时预建等于常年 25% CPU 空转。只在"有人真要打开"时建 |
| 前端 | `prefetch.js` 最后一步发这个 POST，超时 10 秒，失败静默 |

效果：用户进页面 → 4 秒后自动触发预建 → 等他点开"反事实对照"（通常几十秒后），计划多半已 READY，页面直接出结果而不是"重建 42% · 约剩 57 秒"。

### 3. 配套

- Java 网关加 `@PostMapping("/traffic/v2/counterfactual/prewarm")`，显式发 POST（空 body 用 `Map.of()`，否则 `decisionRequest` 会落到 GET 分支 → 405）。
- `main.py` 的 `threading` 提升到模块级（`_startup_warm` 里原来只有局部导入，后台线程要用）。
- 新增护栏 `frontend/tests/prefetch116.test.mjs`（4 条）：预建必须 POST + 后台线程 + 节流、Java 必须给非 null body、预热顺序不许乱、挂载点必须调用。

## 三、已知边界

| 项 | 说明 |
|---|---|
| 预建不是"永久热" | 计划 key 含雷达帧与天气快照，帧一变（约 6 分钟）就要重建。所以预建只在"有人进页面"时触发，不做定时 |
| 预建可能撞上用户点击 | 若用户在 4 秒内就点开对照页，仍会看到 `BUILDING` —— 前端本来就有轮询与"改看全国层"按钮兜底 |
| 预取不覆盖城市层下钻 | 逐市载荷按作用域缓存，预取只热全国层；下钻第一下仍要几百毫秒 |
| 运行日志页仍会显示建场进度 | 它依赖旧轨 `traffic_service.session()`；预建正是为了把它提前算掉，但日志页与对照页的 key 不一定相同 |
| 预取的 4 秒延迟是经验值 | 1366 投影下首屏约 2–3 秒完成；4 秒后启动可避开主载荷。若现场机器特别慢，预取会稍晚，不影响正确性 |
